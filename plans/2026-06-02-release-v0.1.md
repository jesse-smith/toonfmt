## Goal
toonfmt is feature-complete for v0.1 (stdio + HTTP upstream, bearer + OAuth + interactive
OAuth, the TOON transform) but has **no distribution story**: no README, no LICENSE, no CI,
no release automation, no public remote. This phase makes it **shippable and installable** —
a one-line `curl | sh` installer for major platforms, a tagged `v0.1.0` GitHub Release with
prebuilt binaries, a front-door README, and a CI gate — so a consumer can install the binary
and point `.mcp.json` at it without a Rust toolchain. **Phase B** (deferred follow-up) adds an
in-binary `toonfmt update` self-update subcommand once a real release exists to update from.

## Architecture
Distribution choice follows the constitution's "single binary (Rust), cleanest `.mcp.json`
story, no runtime to install" decision (ARCHITECTURE.md "Language / distribution"). Nothing in
the proxy core, transform, or OAuth paths changes — this phase is **packaging + docs + CI only**.

**Decisions settled with the user (this brainstorm, 2026-06-02):**

- **`dist` (formerly `cargo-dist`) drives release + installers.** Chosen over a hand-rolled
  `taiki-e/upload-rust-binary-action` matrix **specifically because the user wants a `curl|sh`
  one-liner** — generating and maintaining cross-platform installer scripts is dist's headline
  feature and exactly what taiki-e does *not* provide. `dist` is actively maintained (v0.32.0,
  2026-05-22) despite a stale prior belief it was abandoned. Sibling project `jesse-smith/dbtoon`
  already runs this pattern and is the working reference.
- **dist version is pinned (v0.32.0), accepted.** dist is self-hosting: `release.yml` is
  *generated by* a pinned dist version and bakes that version into the installer URL. There is
  **no at-latest mode** — pinning guarantees a tag produces a byte-reproducible release. Bumping
  is an explicit, reviewable `dist init` re-run ("Always Be Initing"). The user prefers at-latest
  generally, but accepts the pin here because release reproducibility is the right trade for the
  *release* tool specifically (distinct from everyday CI action versioning).
- **Crypto stays aws-lc-rs.** The dep tree resolves to rustls + aws-lc-rs (verified: no OpenSSL
  anywhere in Cargo.lock). aws-lc-rs carries a C/asm component, but its only practical cost is
  *cross-compilation* — which the **native-runner** build matrix sidesteps entirely. `ring` (also
  C, easier to cross-build) is the documented fallback **iff** a target gives trouble; pure-Rust
  providers (`rustls-rustcrypto`) were rejected on audit-maturity grounds for a binary whose job is
  carrying OAuth/bearer tokens over TLS. **No code change** unless a build actually breaks.
- **License = MIT.** Verified unblocked: all 227 deps are permissive (MIT/Apache/ISC/BSD/Unicode/
  Zlib); the lone `r-efi … OR LGPL` is an `OR` (pick MIT) on a UEFI crate that never compiles into
  the core-4 targets; the lone CDLA-Permissive crate is permissive cert data.
- **No Codecov at v0.1** (deferred; recorded in memory `codecov-deferred.md`). A new repo has no
  `CODECOV_TOKEN`, and dbtoon's `fail_ci_if_error: true` would make CI red on day one. CI ships the
  clippy + test gate only.
- **CI action tags are at-latest** (`@v1`-style moving majors), honoring the user's preference —
  only dist's *own* version is necessarily pinned.
- **Self-update is Phase B (deferred), not v0.1.** It depends on the dist installer's *install
  receipt* existing, so it's only testable end-to-end once a real release with installer assets is
  published — naturally its own slice after the first tag. `install-updater` stays `false`
  (dist's standalone updater binary); self-update is instead an **in-binary `toonfmt update`
  subcommand** using the `axoupdater` crate as a library, mirroring dbtoon's `src/update.rs`. This
  matches the constitution's single-binary ethos (no second `toonfmt-update` executable).

**Core-4 targets** (all native GitHub runners — no cross-compile, keeps aws-lc-rs happy):
`aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`.
musl / linux-arm64 are deliberately out of v0.1 scope (aws-lc-rs cross-build friction; add on request).

## Tech Stack
- **`dist` v0.32.0** — release pipeline + shell/PowerShell installer generation. Config in
  `dist-workspace.toml`; generates `.github/workflows/release.yml`. Installed locally via
  `cargo install cargo-dist` (or the dist installer) to run `dist init`.
- **GitHub Actions** — `release.yml` (dist-generated, tag-triggered) + `ci.yml` (hand-written).
- **`actions-rust-lang/setup-rust-toolchain@v1`** — CI toolchain (clippy component).
- **`gh` CLI** — create the remote repo, verify `gh auth status` before push/PR.
- **`axoupdater` ^0.9** (`github_releases`, `blocking`; `default-features = false`) — **Phase B only**.

## Acceptance criteria
<!-- What cairn-accept checks before "landed". Conditions, not steps. -->

### Phase A
- A public GitHub repo exists with `main` pushed; `ci.yml` is green (clippy `-D warnings` + `cargo test` pass).
- `LICENSE` (MIT) present at root; `Cargo.toml` has `license = "MIT"` + description/repository/readme metadata; `cargo build` clean.
- `README.md` exists as the front door: pitch, working install one-liner, the four `.mcp.json` recipes, how-it-works, MIT license.
- A `v0.1.0` GitHub Release exists with: prebuilt archives + checksums for all core-4 targets, generated shell + PowerShell installers, and a working `curl | sh` one-liner that installs a runnable `toonfmt`.
- The released binary runs the existing functionality (the proxy/transform/OAuth paths are unchanged — verified by the already-landed test suite passing in CI, not re-tested here).
- No regression: `cargo test` + `cargo clippy -- -D warnings` green.

### Phase B (when undertaken)
- `toonfmt update` exists: updates an installer-based install in place to the latest GitHub Release; on a source/`cargo install` build (no receipt) it exits gracefully with guidance rather than erroring or clobbering.
- Network-failure and no-installer-for-platform cases produce clear errors, not panics.
- No regression in the serve/login/transform paths; `cargo test` + clippy green.
